# Gairus on Render: prepared deployment

This is a prepared configuration, not a deployed service or purchase.
The owner delegated the technical choice on 2026-10-25. Recurring charges still
require specific approval before creating resources.
The full 49-test suite passed locally under Python 3.12 and Python 3.14,
including six checks of this configuration. Render's live build and validation
remain to be performed after account access and spending approval.

## Selected topology

- One Docker web service, Frankfurt, 0.5 CPU and 512 MB RAM.
- One persistent disk of 1 GB mounted at `/app/data`.
- One instance only, consistent with SQLite and the single-instance disk.
- Source: `repair/cloud-hardening-20261025`, not `main`.
- Automatic deploys disabled; pushing this file does not launch or buy a service.
- Owner and ORTA keys generated by Render, never committed to source.
- Autonomy disabled and approvals enabled. No AI or Slack production credentials
  are preloaded or activated.
- Intended hostname: `gairus.zyrvion.io`. Register the hostname with the new
  service and confirm its actual Render DNS target before editing Spaceship.

The Blueprint fields and generated 256-bit secrets follow the
[Render Blueprint specification](https://render.com/docs/blueprint-spec).
Persistent disks require a paid service; only files under the disk's mount
path survive redeployments
([Render disk documentation](https://render.com/docs/disks)).

## Access, consent and account ownership

Keep the service and billing in the owner's Render account, not a third party's.
If an account must be created, the owner must approve account creation and
acceptance of terms. Use secure credential handling for a Render API key;
never request it in Slack. No Render credential is currently available.

DNS is currently delegated to Spaceship. API automation, if approved, needs
only DNS record read/write permissions, not registration, renewal, transfer,
nameserver or billing access
([Spaceship API documentation](https://docs.spaceship.dev/)).
Use its authenticated API or an explicitly approved account session.
No Spaceship credential is currently available.

Before an API DNS write, read and save the existing zone privately, confirm
the exact CNAME schema and update semantics, and check for conflicts.
Change only the approved Gairus hostname. Never replace the entire zone, use
force mode, or change apex, `www`, MX, TXT or nameservers to make this work.
The target must come from the created Render service; it must not be guessed.

## Controlled rollout

1. Obtain approval for the specific base service and any account creation.
2. Obtain secure Render access and check existing workspace resources/billing.
3. If a service already exists, inspect it and its data before modifying it.
4. Back up any existing databases; do not silently import database files
   committed to the public Git repository.
5. Create the approved service from the repair branch with the prepared disk.
6. Verify health, owner access, default-deny API behavior and the absence of
   secrets in build logs, public files and response bodies.
7. Create a synthetic mission and memory; restart/redeploy and verify both
   survive. Perform a consistent SQLite backup/restore test.
8. Register `gairus.zyrvion.io` with the service, then change only its verified
   DNS records through the authorized Spaceship account.
9. Verify public DNS, HTTPS certificate, hostname and authentication.
10. Add the owner's chosen AI-provider and Slack credentials only after
    separate authorized access. Verify real operations before calling the
    assistant functional or enabling autonomy.

Render snapshots a disk daily and retains snapshots for seven days; this
must not be represented as a tested SQLite recovery strategy
([Render disk documentation](https://render.com/docs/disks)).
Prepare consistent database backups and verify recovery before production use.
